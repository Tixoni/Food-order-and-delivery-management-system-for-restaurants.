# Система управления заказами и доставкой еды для ресторанов

Курсовая работа по дисциплине «Архитектура клиент-серверных приложений», РТУ МИРЭА, тема 19.

## Архитектура

Сервисная архитектура укрупнённой гранулярности с событийно-ориентированным ядром: четыре сервиса по бизнес-возможностям плюс шлюз. Обоснование выбора и сравнение с альтернативами — в отчёте, раздел 2.

| Компонент      | Ответственность                                                          |
| -------------- | ------------------------------------------------------------------------ |
| `gateway`      | Единая точка входа, GraphQL BFF, WebSocket, ограничение частоты запросов |
| `catalog`      | Рестораны, меню, модификаторы, стоп-листы, зоны доставки                 |
| `order`        | Корзина, заказ, конечный автомат статусов, оркестратор саги, таймеры     |
| `payment`      | Платёжные операции, идемпотентность, интеграция с платёжным шлюзом       |
| `delivery`     | Курьеры, геопозиция, подбор, назначение, отслеживание                    |
| `notification` | Уведомления (опционально)                                                |

## Стек

TypeScript, NestJS, TypeORM, React + Vite, GraphQL, WebSocket, Apache Kafka, PostgreSQL + PostGIS, Redis, OSRM/OpenStreetMap, OAuth 2.0/JWT, Docker Compose, nginx, Keycloak, Prometheus, Grafana, Jaeger, Jest, k6.

Межсервисные синхронные вызовы в прототипе — внутренний HTTP с явными DTO; gRPC оставлен как вариант развития.

## Базы данных

Принцип «база на сервис»: ни один сервис не читает чужие таблицы, внешних ключей между базами нет. В прототипе — четыре логические базы на одном экземпляре PostgreSQL 16 + PostGIS.

| База          | Сервис     | Основные таблицы                                                                                                 |
| ------------- | ---------- | ---------------------------------------------------------------------------------------------------------------- |
| `catalog_db`  | `catalog`  | рестораны, расписание, зоны доставки (полигоны PostGIS), категории, блюда, модификаторы, журнал стоп-листа       |
| `order_db`    | `order`    | заказы со снимками цен, история статусов, состояние саги и её шаги, персистентные таймеры, ключи идемпотентности |
| `payment_db`  | `payment`  | платежи и неизменяемый журнал операций (холд, списание, возврат, снятие холда); данных карт нет                  |
| `delivery_db` | `delivery` | курьеры с геопозицией, смены, история координат, доставки, предложения курьерам                                  |

Во всех четырёх базах — таблицы `outbox_messages` и `inbox_messages`: событие пишется в одной транзакции с изменением данных (Transactional Outbox), повторная доставка отсекается по идентификатору сообщения.

Что заложено в схему:

- пространственные индексы GiST: «рестораны, доставляющие по адресу» и «ближайший свободный курьер в радиусе 3 км»;
- идемпотентность на уровне уникальных индексов: повторная отправка формы не создаёт второй заказ, повтор платёжной операции не списывает деньги дважды;
- оптимистичная блокировка (`version`) против гонки «кухня подтверждает — клиент отменяет»;
- частичные индексы для очередей: неопубликованные события, несработавшие таймеры, активные заказы;
- деньги — целые копейки, проверки целостности сумм на уровне базы.

```bash
npm run env:up       # PostgreSQL + PostGIS, Redis, Kafka
npm run db:migrate   # схема всех четырёх баз; повторный запуск безопасен
npm run db:seed      # 50 ресторанов, ~1500 блюд, 20 курьеров
```

Миграции — `infra/migrations/`, каждая выполняется в своей транзакции; конвейер CI применяет их к чистой базе и проверяет, что повторный запуск ничего не меняет.

## Структура репозитория

```
apps/         сервисы и клиентское приложение
packages/     общие контракты, утилиты, тестовые помощники
infra/        описание окружения, миграции, генератор данных, нагрузочные сценарии

```

## Запуск

Требования: Docker, Node.js 20+, 8 ГБ ОЗУ.

```bash
docker compose -f infra/compose/docker-compose.yml --profile core up -d
```

Профили окружения: `core`, `auth`, `observability`, `geo`, `full`.

Регистрация клиента идёт через шлюз и требует подтверждения e-mail. Письма в окружении разработки никуда не уходят — их ловит Mailpit: http://localhost:18025. Учётные записи для проверки ролей описаны в `infra/keycloak/realm-food-delivery.json`; Keycloak загружает этот файл только при первом запуске, поэтому после его изменения том `keycloak-data` нужно пересоздать (`npm run env:reset`).

## Статус

- готово: окружение, схема всех баз, сервис `catalog` (меню, стоп-листы, геозоны, Outbox, кэш), шлюз GraphQL для каталога, аутентификация через Keycloak, регистрация клиента с подтверждением e-mail;
- готово: сервис `order` — конечный автомат заказа, оркестрованная сага с компенсациями, персистентные таймеры статусов, идемпотентное оформление, корзина, команды кухни и оператора; платежи и доставка пока подключены заглушками с тем же контрактом;
- готово: общие механизмы устойчивости — размыкатель цепи и повторы для межсервисных вызовов, очередь необработанных сообщений (DLQ), единый публикатор Transactional Outbox;
- готово: веб-приложение — витрина клиента (адрес, рестораны по зоне доставки, меню с модификаторами, корзина) и панель ресторана (меню, стоп-лист, зоны доставки на карте, регистрация ресторанов);
- впереди: сервисы платежей и доставки, оформление заказа через шлюз GraphQL, экраны кухни и курьера, отслеживание, нагрузочные проверки.

Сквозные проверки на живых процессах:

- сервис заказов — `node infra/verification/order-e2e.mjs` (сценарии `happy`, `capture-failure`, `timeout-start`/`timeout-check`);
- регистрация с подтверждением e-mail — `node infra/verification/auth-register-e2e.mjs`.
