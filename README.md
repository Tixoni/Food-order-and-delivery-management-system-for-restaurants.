# Система управления заказами и доставкой еды для ресторанов

Курсовая работа по дисциплине «Архитектура клиент-серверных приложений», РТУ МИРЭА, тема 19.

## Архитектура

Сервисная архитектура укрупнённой гранулярности с событийно-ориентированным ядром: четыре сервиса по бизнес-возможностям плюс шлюз. Обоснование выбора и сравнение с альтернативами — в отчёте, раздел 2.

| Компонент      | Ответственность                                                          |
| -------------- | ------------------------------------------------------------------------ |
| `gateway`      | Единая точка входа, GraphQL BFF, WebSocket, ограничение частоты запросов |
| `catalog`      | Рестораны, меню, модификаторы, стоп-листы, зоны доставки                 |
| `order`        | Корзина, заказ, конечный автомат статусов, оркестратор саги, таймеры     |
| `payment`      | Платёжные операции, идемпотентность, интеграция с платёжным шлюзом       |
| `delivery`     | Курьеры, геопозиция, подбор, назначение, отслеживание                    |
| `notification` | Уведомления (опционально)                                                |

## Стек

TypeScript, NestJS, TypeORM, React + Vite, GraphQL, WebSocket, Apache Kafka, PostgreSQL + PostGIS, Redis, OSRM/OpenStreetMap, OAuth 2.0/JWT, Docker Compose, nginx, Keycloak, Prometheus, Grafana, Jaeger, Jest, k6.

Межсервисные синхронные вызовы в прототипе — внутренний HTTP с явными DTO; gRPC оставлен как вариант развития.

## Базы данных

Принцип «база на сервис»: ни один сервис не читает чужие таблицы, внешних ключей между базами нет. В прототипе — четыре логические базы на одном экземпляре PostgreSQL 16 + PostGIS.

| База          | Сервис     | Основные таблицы                                                                                                 |
| ------------- | ---------- | ---------------------------------------------------------------------------------------------------------------- |
| `catalog_db`  | `catalog`  | рестораны, расписание, зоны доставки (полигоны PostGIS), категории, блюда, модификаторы, журнал стоп-листа       |
| `order_db`    | `order`    | заказы со снимками цен, история статусов, состояние саги и её шаги, персистентные таймеры, ключи идемпотентности |
| `payment_db`  | `payment`  | платежи и неизменяемый журнал операций (холд, списание, возврат, снятие холда); данных карт нет                  |
| `delivery_db` | `delivery` | курьеры с геопозицией, смены, история координат, доставки, предложения курьерам                                  |

Во всех четырёх базах — таблицы `outbox_messages` и `inbox_messages`: событие пишется в одной транзакции с изменением данных (Transactional Outbox), повторная доставка отсекается по идентификатору сообщения.

Что заложено в схему:

- пространственные индексы GiST: «рестораны, доставляющие по адресу» и «ближайший свободный курьер в радиусе 3 км»;
- идемпотентность на уровне уникальных индексов: повторная отправка формы не создаёт второй заказ, повтор платёжной операции не списывает деньги дважды;
- оптимистичная блокировка (`version`) против гонки «кухня подтверждает — клиент отменяет»;
- частичные индексы для очередей: неопубликованные события, несработавшие таймеры, активные заказы;
- деньги — целые копейки, проверки целостности сумм на уровне базы.

```bash
npm run env:up       # PostgreSQL + PostGIS, Redis, Kafka
npm run db:migrate   # схема всех четырёх баз; повторный запуск безопасен
npm run db:seed      # 50 ресторанов, ~1500 блюд, 20 курьеров
```

Миграции — `infra/migrations/`, каждая выполняется в своей транзакции; конвейер CI применяет их к чистой базе и проверяет, что повторный запуск ничего не меняет.

## Структура репозитория

## Запуск

Требования: Docker, Node.js 20+, 8 ГБ ОЗУ.

```bash
docker compose -f infra/compose/docker-compose.yml --profile core up -d
```

Профили окружения: `core`, `auth`, `apps`, `geo`, `observability`, `full`.

В профилях `apps` и `full` единственный вход — обратный прокси nginx: http://localhost:13080 отдаёт клиентское приложение, GraphQL с подписками и вход `/auth`. Шлюз и каталог запущены в двух репликах (SCAL-2): прокси распределяет запросы и обходит выключенную реплику, внутренний порт прокси 8081 балансирует обращения к каталогу от шлюза и `order`. Шлюз наружу не публикуется — он доверяет адресу клиента из заголовка прокси (`TRUST_PROXY_HOPS=1`).

Журналы всех сервисов — в одном месте (профиль `observability`): сервисы пишут JSON в стандартный вывод, Alloy собирает вывод контейнеров проекта в Loki, Grafana — http://localhost:13030, дашборд «Журнал действия»: все записи одного действия пользователя по сквозному идентификатору (`x-correlation-id`, есть в каждом ответе). Телефон, адрес, токены и пароли в журнал не попадают — маскируются.

Маршрутизатор OSRM (профиль `geo`) читает подготовленную карту Москвы: один раз выполните `npm run osrm:prepare` (≈85 МБ карты, ≈1 мин подготовки, ≈270 МБ в `infra/osrm/data`, в git не попадает). Без маршрутизатора система работает: подбор курьера и прогноз считаются по прямой.

Регистрация клиента идёт через шлюз и требует подтверждения e-mail. Письма в окружении разработки никуда не уходят — их ловит Mailpit: http://localhost:18025. Учётные записи для проверки ролей описаны в `infra/keycloak/realm-food-delivery.json`; Keycloak загружает этот файл только при первом запуске, поэтому после его изменения том `keycloak-data` нужно пересоздать (`npm run env:reset`).

## Статус

- готово: окружение, схема всех баз, сервис `catalog` (меню, стоп-листы, геозоны, Outbox, кэш), шлюз GraphQL для каталога, аутентификация через Keycloak, регистрация клиента с подтверждением e-mail;
- готово: сервис `order` — конечный автомат заказа, оркестрованная сага с компенсациями, персистентные таймеры статусов, идемпотентное оформление, корзина, команды кухни и оператора; с сервисами платежей и доставки работает по HTTP (`PAYMENT_MODE` / `DELIVERY_MODE=stub` — заглушки с тем же контрактом);
- готово: сервис `payment` — холд, списание, снятие холда, частичный и полный возврат с неизменяемым журналом операций, идемпотентность по ключу, сверка незавершённых операций с провайдером; эмулятор платёжного провайдера с контрактом ЮKassa и управляемыми отказами;
- готово: общие механизмы устойчивости — размыкатель цепи и повторы для межсервисных вызовов, очередь необработанных сообщений (DLQ), единый публикатор Transactional Outbox;
- готово: веб-приложение — витрина клиента (адрес, рестораны по зоне доставки, меню с модификаторами, корзина) и панель ресторана (меню, стоп-лист, зоны доставки на карте, регистрация ресторанов);
- готово: оформление заказа из браузера через шлюз GraphQL — корзина, оформление, история заказов, экран отслеживания с отменой до начала готовки;
- готово: сервис `delivery` — смены курьеров, подбор ближайшего свободного в радиусе 3 км по пространственному индексу, предложения с таймером 90 с и переназначением, отметки «забрал» и «доставил», позиция курьера в Redis с рассылкой в канал заказа;
- готово: экран кухни (`/kitchen`), приложение курьера (`/courier`, PWA) и отслеживание заказа на карте; статусы, очередь кухни, предложения курьеру и позиция курьера приходят подписками GraphQL по WebSocket (`graphql-ws`); сквозной сценарий «клиент → кухня → курьер → доставлен» проходит в браузере;
- готово: маршрутизатор OSRM за размыкателем цепи — заказ предлагается курьеру, который раньше доедет по дорогам с учётом его транспорта, маршрут «ресторан → клиент» на картах курьера и клиента, прогноз доставки по длине маршрута; без OSRM — по прямой;
- впереди: устойчивость и наблюдаемость, нагрузочные проверки.

Сквозные проверки на живых процессах:

- сервис заказов — `node infra/verification/order-e2e.mjs` (сценарии `happy`, `capture-failure`, `payment-down`, `timeout-start`/`timeout-check`);
- сервис платежей и эмулятор провайдера — `node infra/verification/payment-e2e.mjs`;
- оформление заказа через шлюз GraphQL — `node infra/verification/checkout-e2e.mjs`;
- доставка: подбор, переназначение, позиция, вручение — `node infra/verification/delivery-e2e.mjs`; режимы отказов эмулятора меняются на лету: `POST http://localhost:13010/_emulator/settings`;
- маршрутизатор: подбор по дорогам, маршрут на экранах, работа при остановленном OSRM — `node infra/verification/routing-e2e.mjs`;
- журналы в одном месте (OBS-1): действие находится по идентификатору во всех сервисах, персональных данных нет — `node infra/verification/obs1-logs.mjs`;
- задержка координаты курьера до клиента по WebSocket (PERF-3, ≤ 2 с) — `node infra/verification/perf3-latency.mjs` (`SAMPLES`, `CLIENTS` — число координат и подписчиков);
- новый заказ на экране кухни после оплаты (PERF-4, ≤ 3 с) — `node infra/verification/perf4-kitchen.mjs`;
- регистрация с подтверждением e-mail — `node infra/verification/auth-register-e2e.mjs`;
- две реплики за прокси (SCAL-2): нагрузка через прокси, реплики гасятся по очереди, подписка и вход переживают отказ, SEC-5 за прокси — `node infra/verification/scal2-replicas.mjs`;
- три интерфейса вместе — вручную: клиент, кухня и курьер в трёх вкладках (у вкладок должны быть разные адреса, например `localhost`, `127.0.0.1` и `127.0.0.2`, — иначе сеансы делят одну куку входа); у курьера галочка «Имитация движения» двигает его к цели без GPS.
