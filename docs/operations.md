# Запуск и восстановление учебного стенда

## Запуск с чистыми томами

После `npm ci` выполните `npm run env:prepare`. Команда поднимает инфраструктуру, применяет миграции, наполняет пустые базы каталога и доставки, привязывает тестовых сотрудников к ресторану и запускает приложение с мониторингом и резервным копированием. Название ресторана выводится при привязке. Чтобы запустить OSRM, сначала подготовьте карту командой `npm run osrm:prepare`, затем используйте `npm run env:prepare -- --geo`. Если образы уже собраны, можно пропустить сборку флагом `--no-build`.

Витрина открывается на http://localhost:13080, Grafana — на http://localhost:13030/d/system-health. Используйте тестовые учётные записи из `infra/keycloak/realm-food-delivery.json`.

Для уже импортированной области `food-delivery` добавьте `http://localhost:13080/login?verified=1` в список Valid redirect URIs клиента `web` в консоли Keycloak. Изменение файла импорта применяется при создании области.

Чистый стенд получает 3 ресторана по 6 блюд рядом с «Тверская, центр». Для прежнего объёма нагрузочных данных запустите подготовку отдельного стенда с переменной `SEED_RESTAURANTS=50`.

`kitchen@food.local` — учётная запись ресторанного табло. Атрибут Keycloak `restaurantId` задаёт ресторан и его очередь. Администратор может выбирать ресторан на странице «Табло кухни».

## Резервное копирование и пробное восстановление

Сервис `backup` берёт снимок всего кластера PostgreSQL вместе с WAL сразу при старте и затем примерно каждые пять минут. Готовый снимок публикуется в том `postgres-backups`. Хранятся последние 12 снимков. Том и исходная БД находятся на одном хосте. Для защиты от потери диска потребуется отдельное хранилище копий.

```bash
docker compose -f infra/compose/docker-compose.yml run --rm -T backup once
docker compose -f infra/compose/docker-compose.yml run --rm -T restore-check
```

Команда сверяет манифест и запускает копию PostgreSQL в одноразовом контейнере, читает таблицы всех четырёх сервисов и выводит возраст снимка и время восстановления. Проверка завершится с ошибкой, если возраст превысит 15 минут либо восстановление займёт больше часа. Данные работающего PostgreSQL остаются доступны во время проверки.

## Разбор DLQ

1. В журнале Grafana найдите ошибку обработки и запишите топик, идентификатор события и сквозной идентификатор запроса. По ним проверьте состояние заказа и саги.
2. Посмотрите соответствующий DLQ на тестовом стенде. Для чтения выберите топик из списка и подставьте его в команду.

   ```bash
   docker compose -f infra/compose/docker-compose.yml exec -T kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server kafka:9092 --list
   docker compose -f infra/compose/docker-compose.yml exec -T kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server kafka:9092 --topic order.events.dlq --from-beginning --max-messages 10 --timeout-ms 3000 --property print.key=true --property print.partition=true --property print.offset=true
   ```

3. Сверьте состояние в сервисе-владельце и причину сбоя. Некорректные сообщения оставьте в DLQ. Для временного сбоя сначала восстановите потребитель и проверьте, выполнил ли он действие. Используйте штатную команду отмены или компенсации, если она применима.
4. Если требуется повторная публикация исправного события, проверьте с разработчиком ключ агрегата и идемпотентность получателя. Повторите одно событие с исходным идентификатором, зафиксируйте результат и проверьте, что эффект произошёл один раз. Массовый повтор не запускается автоматически.
